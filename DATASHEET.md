# Datasheet — BBO Capstone Query Dataset

## Motivation

**Why was this dataset created?**

This dataset was created to support the Black-Box Optimisation (BBO) challenge of the
Imperial College London Professional Certificate in Machine Learning and AI. The task
is to find input values that maximise eight unknown synthetic functions, where the
internal structure of each function is hidden and can only be probed by submitting
query points and observing the returned output.

The dataset is not a pre-existing resource that was collected for general use. It is a
record of my own interaction with the challenge: the points I chose to query, and the
outputs those queries returned. It exists to make my optimisation process reproducible
and auditable, and to allow the surrogate model to be rebuilt from scratch at any time.

**What task does it support?**

Sequential decision-making under uncertainty. Specifically, it supports fitting a
Gaussian Process surrogate per function, from which the next query point is selected.
It also supports the secondary diagnostic analyses I ran (SVM kernel comparison,
linear-vs-neural-network fit comparison, feature importance ranking).

## Composition

**What does the dataset contain?**

Two distinct parts.

*Initial data (provided by the course).* Eight pairs of NumPy `.npy` files, one pair
per function, containing input vectors and their corresponding scalar outputs:

| Function | Dimensionality | Initial points |
|---|---|---|
| 1 | 2D | 10 |
| 2 | 2D | 10 |
| 3 | 3D | 15 |
| 4 | 4D | 30 |
| 5 | 4D | 20 |
| 6 | 5D | 20 |
| 7 | 6D | 30 |
| 8 | 8D | 40 |

*Weekly query data (generated by me).* One additional observation per function per
week, across 13 weekly rounds. Stored as JSON, one file per function, containing the
full accumulated history of input vectors and observed outputs — initial points and
weekly queries combined, in chronological order.

**Size and format**

At completion: 175 initial points plus 104 weekly observations (8 functions × 13
rounds), for 279 total observations. Inputs are real-valued vectors with between 2 and
8 components. Outputs are single real-valued scalars. Initial data is `.npy`; the
working history is JSON.

**Are there gaps?**

Yes, and they matter for interpretation.

Coverage is extremely uneven relative to dimensionality. Function 1 has 23 points
covering 2 dimensions; Function 8 has 53 points covering 8 dimensions. The latter is
sparse to the point where large regions of the input space are entirely unsampled.

Sampling is also deliberately non-uniform. Because queries were selected by an
optimisation algorithm rather than at random, points cluster in regions that returned
high outputs. For Function 4, recent queries fall within a narrow band around
x ≈ 0.35–0.42 in all four dimensions. This is the intended behaviour of exploitation,
but it means the dataset is not a representative sample of each function's behaviour
across its domain.

There is one known redundancy: Function 5 received an identical input in two
consecutive rounds, producing a duplicate observation that added no information.

## Collection process

**How were the queries generated?**

Each weekly query was produced by a Gaussian Process surrogate with an Expected
Improvement acquisition function (`scikit-optimize`), fitted to all observations
available for that function at the time. The ask-tell workflow was: request a suggested
point, submit it to the course platform, wait for the output, record the result, repeat.

A minority of queries were chosen manually, overriding the model's suggestion. These
were diagnostic: for Function 5, I deliberately tested points at specific combinations
of domain boundaries (all coordinates at 0, one at 1, all at 1, all at 0.5) to test a
hypothesis about the function's structure. These overrides are identifiable in the
history but are not flagged as such in the data itself — a limitation noted below.

**Over what time frame?**

Thirteen weekly rounds, corresponding to Modules 12 to 24 of the programme
(approximately July to October 2026). The platform processed one submission per week,
with results returned by email before the next submission window opened.

## Preprocessing and uses

**Transformations applied**

None to the stored data. Inputs and outputs are recorded exactly as submitted and
returned, to six decimal places for inputs and at full returned precision for outputs.

Transformations are applied downstream at model-fitting time only: outputs are negated
before being passed to `scikit-optimize` (which minimises by default, while all eight
functions are maximisation problems), and inputs and outputs are standardised before
fitting the SVM and neural network diagnostics. The raw values remain unmodified on
disk.

**Intended uses**

Reconstructing the optimisation trajectory; refitting the surrogate model; analysing
how exploration and exploitation balanced across functions of differing dimensionality;
and supporting the structural findings documented in the repository.

**Inappropriate uses**

This dataset should not be used to characterise the eight functions in general. It is a
biased, adaptively-chosen sample concentrated in high-performing regions, not a
representative survey of each function's behaviour. Any claim about global function
structure drawn from it would be unsound, particularly for the higher-dimensional
functions where coverage is sparse.

It also should not be treated as a benchmark for comparing optimisation algorithms,
since the query sequence reflects one specific strategy including manual interventions.

## Distribution and maintenance

**Availability and terms of use**

The weekly query history is available in this repository. The initial `.npy` datasets
were provided by the course and are included for reproducibility; their redistribution
terms are set by the course provider, not by me.

**Maintenance**

Maintained by Riccardo Prenza (github.com/rprenza) as part of the capstone submission.
The dataset is complete at 13 rounds and is not expected to grow further. Corrections,
if needed, would be made by commit to this repository, with the change visible in
version history.

Two corrections have already been applied during the project: a duplicate observation
recorded in error was removed on two separate occasions, using a dedicated undo
function. These corrections are visible in the commit history.
